# Database reference — YourMarket

The project ships one SQL file: [`database/schema.sql`](../database/schema.sql).
Create the database and database user manually in your hosting panel, then import
this file through phpMyAdmin. It contains the full table definitions and default
store settings, but no administrator, customer, demo product, or seeded login.
The first public registration becomes the administrator; later registrations
are customers and require email verification. The web installer also imports
this same schema. Optional demo records can be generated from **Admin → Tools**
or `tools/seed.php`.

* Engine: InnoDB, `utf8mb4` / `utf8mb4_unicode_ci`
* 27 tables, 1 optional configurable prefix (`db.prefix`, empty by default)
* All access goes through PDO prepared statements — see
  [SECURITY.md](SECURITY.md#sql-injection)

---

## 0. Creating and importing the database

1. In the hosting control panel, create a MySQL/MariaDB database and a dedicated user with privileges on that database.
2. Select the database in phpMyAdmin and import `database/schema.sql`.
3. Configure `config/config.php` with the actual database connection details.
4. Open the storefront registration page and immediately create the first account. That account is granted the administrator role; later self-registrations are customers.

`schema.sql` is safe to re-import: it creates missing tables, adds the required first-login password flag when upgrading older `users` tables, seeds only missing setting rows, and updates only exact untouched legacy brand defaults. Existing custom setting values and user rows are preserved. Back up before importing into a database already containing data.

The SQL is compatible with MySQL 5.7/MariaDB, includes its charset and time-zone setup, and does not create the database itself or use `DEFINER`, routines, or `SUPER` privileges.

## 1. Credentials checklist

Fill this in and keep it out of version control (`config/config.php` is
git-ignored and HTTP-blocked).

| Setting | Value | Notes |
| --- | --- | --- |
| `db.host` | `sql306.hstn.me` (aeonfree) / `localhost` elsewhere | some hosts need `127.0.0.1` or a socket path |
| `db.port` | `3306` | rarely `3307` on shared hosting |
| `db.name` | `mseet_43261025_softmymarket` | shared hosts prefix DB names with the account |
| `db.user` | `mseet_43261025` | **not** `root` in production |
| `db.pass` | *(20+ random chars)* | rotate after the site is live |
| `db.prefix` | *(empty)* | only set this if you must share one database |
| `app.key` | *(64 hex chars)* | generated by the installer; back it up |
| `app.url` | `https://www.softmymarket.lk` | no trailing slash |
| Charset | `utf8mb4` | enforced by the schema |

Least-privilege grants (VPS):

```sql
CREATE DATABASE softmymarket CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'smm_app'@'localhost' IDENTIFIED BY '<strong-password>';
GRANT SELECT, INSERT, UPDATE, DELETE ON softmymarket.* TO 'smm_app'@'localhost';
FLUSH PRIVILEGES;
```

Schema installs need `CREATE`, `ALTER`, `INDEX`, `DROP` — run
`database/schema.sql` as a privileged user once, then switch the app to the
`SELECT/INSERT/UPDATE/DELETE` account above.

Environment overrides (useful on staging) skip the config file entirely:

```bash
SMM_DB_HOST=127.0.0.1 SMM_DB_NAME=softmymarket_test SMM_DB_USER=root SMM_DB_PASS=secret php tests/run.php --db
```

| Table | Purpose | Key columns |
| --- | --- | --- |

| `brands` | Brand directory | `name`, `slug` UNIQUE |

### Orders and money

| Table | Purpose | Key columns |
| --- | --- | --- |

## 3. Order status pipeline

`PENDING → CONFIRMED → PROCESSING → PACKED → SHIPPED → OUT_FOR_DELIVERY → DELIVERED`,
with `CANCELLED` / `REFUNDED` as terminal branches. `Orders::TRANSITIONS` in
`includes/Orders.php` is the allow-list; `OrderService::updateStatus()` writes the
`orders` row, stamps the matching `*_at` column and appends an `order_events`
row inside one transaction. That event row is what the customer sees on
`/track.php` and what the admin/user live boards stream.

Return requests use a separate lifecycle stored in `return_requests` and
`return_events`: `REQUESTED → APPROVED → IN_TRANSIT → RECEIVED → INSPECTING`,
then an outcome of `REFUNDED`, `EXCHANGED`, `REJECTED` or `CLOSED` (with
cancellation before processing). Customers can request return of eligible
quantities within 7 days of delivery. Refund amounts are recorded for manual
reconciliation; no payment-provider refund is triggered. Returned inventory is
added back only when staff explicitly marks it restockable at refund/exchange.

## 4. Category tree behaviour

Categories use the adjacency list plus a materialised `path` and `depth`:

```
id 1  Electronics        parent NULL  depth 0  path /
id 4  Computers          parent 1     depth 1  path /1/
id 9  Gaming Laptops     parent 4     depth 2  path /1/4/
```

* `Catalog::createCategory()` computes `depth` and `path` from the parent.
* `Catalog::categoryDescendantIds($id)` walks the tree once and returns every
  descendant id, so a parent category page lists products from all levels.
* Deleting a parent re-parents children (FK `ON DELETE SET NULL`) — the admin UI
  warns before doing it.
* There is no depth limit; the category screen renders recursively.

## 5. Data integrity rules worth remembering

* `order_items` snapshots title/slug/sku/image/price. Deleting a product never
  corrupts order history (`ON DELETE SET NULL` on `product_id`).
* `coupon_redemptions` has **no** unique constraint on `(coupon_id, order_id)`; the per-user limit is enforced in `Coupons::validate()` inside the checkout transaction.
* `payments.gateway` stores the **config key** (`seylan`, `bank_transfer`,
  `payhere`, `koko`, `payzy`, `mintpay`, `cod`) and `orders.payment_method` stores the
  storefront code (`CARD_SEYLAN`, `PAYHERE`, `BANK_TRANSFER`, `KOKO`, `PAYZY`, `MINTPAY`,
  `COD`). `PaymentManager::methodCode()` / `::keyForMethod()` translate both ways.
* Money is `DECIMAL(12,2)`; never sum floats in PHP without `Pricing::round()`.
* Every FK is indexed; the hot storefront queries are covered by
  `(status, deleted_at, created_at)` and `(category_id, status)` on `products`.

## 6. Seeding

On a host without SSH, use **Admin → Tools → Seed demo data** (the same
generator, batched to survive a 30-second execution limit) or use **Admin → Tools → Seed demo data** after the first administrator account has been created.


```bash
php tools/seed.php                                     # small demo set
php tools/seed.php --products=10000 --customers=10000 --orders=250
php tools/seed.php --products=10000 --force            # append to existing data
```

The seeder creates:

* the full category tree (10 departments → 35+ sub-categories → 3rd level),
* 28 brands,
* products with deterministic SKUs (`SMM-000123`), Drive-style image URLs and
  JSON specs,
* customers with bcrypt `Password123!`, one saved address each,
* orders with items, payments, timeline events and coupon redemptions,
* an `inventory_movements` opening-stock row per product,
* the 5 demo coupons (`WELCOME10`, `SOFTDEALZ15`, `FREESHIP`, `FLASH5K`, expired
  `AVURUDU20`).

## 7. Checking the database

```bash
php tests/run.php --db
```

Runs read-only integrity checks: all 27 tables exist, no orphaned categories,
category depths are consistent, products point at real categories/brands, every
password is a real hash, order subtotals equal their line items, every order has
a timeline event, and the pricing engine's arithmetic balances.

## 8. Maintenance

```sql
-- size per table
SELECT table_name, table_rows,
       ROUND((data_length + index_length) / 1024 / 1024, 2) AS mb
FROM information_schema.tables
WHERE table_schema = DATABASE()
ORDER BY (data_length + index_length) DESC;

-- slow-query sanity: products without a category (should be 0)
SELECT COUNT(*) FROM products p
LEFT JOIN categories c ON c.id = p.category_id WHERE c.id IS NULL;

-- clear rate limits after a lockout
DELETE FROM rate_limits WHERE bucket = 'login';
```

Backups: see [DEPLOYMENT.md §13](DEPLOYMENT.md#13-backups).
